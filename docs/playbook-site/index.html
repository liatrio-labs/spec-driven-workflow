THE SPEC-DRIVEN DEVELOPMENT (SDD) PLAYBOOK

This website outlines the Spec-Driven Development (SDD) workflow as envisioned by Liatrio. SDD is a systematic process designed to guide a feature from initial concept to a fully validated, production-ready state. The strategic importance of this workflow lies in its rigorous, phase-based structure that transforms an abstract idea into a tangible, merge-ready feature.

By prioritizing clear requirements, verifiable progress, and evidence-based quality assurance, the SDD process ensures that all stakeholders are aligned, development is predictable, and the final product meets its intended goals with exceptional quality. This playbook details the four distinct phases: Specification, Task Breakdown, Implementation, and Validation.

You can experience the workflow yourself at https://github.com/liatrio-labs/spec-driven-workflow.

THE FOUR PHASES OF SDD

01

PHASE 1: SPECIFICATION

Objective: Define the "what" and "why" of the feature, establishing clear boundaries and functional requirements.

Responsible Role: Feature Lead

Primary Artifact: A specification document detailing Goals, User Stories, Demoable Units, Functional Requirements, and Technical Considerations.

Acceptance Gate: Sign-off from Feature Lead and key stakeholders, locking the scope as the single source of truth.

02

PHASE 2: TASK BREAKDOWN

Objective: Deconstruct the specification into a sequential list of demoable parent tasks and granular sub-tasks.

Responsible Role: Technical Lead or Implementer

Primary Artifact: A task list document identifying all relevant files and providing a comprehensive checklist of parent and sub-tasks.

Acceptance Gate: Technical Lead and implementing team approve the complete task list, confirming it is technically sound and comprehensive.

03

PHASE 3: IMPLEMENTATION

Objective: Execute the task list to produce working code while creating comprehensive proof artifacts.

Responsible Role: Implementer

Primary Artifacts: Task-aligned Git commits with conventional messages and proof documents containing outputs, screenshots, and verification steps.

Acceptance Gate: Every task marked complete with corresponding proof artifact and task-aligned git commit generated and linked.

04

PHASE 4: VALIDATION

Objective: Provide an evidence-based verdict on whether implementation meets all functional requirements and repository standards.

Responsible Role: Reviewer or QA Lead

Primary Artifact: A validation report with executive summary, detailed coverage matrix, and list of any issues found.

Acceptance Gate: Validation Report returns overall PASS status, confirming all requirements met and formal approval to merge.

The upfront investment in clarity de-risks the entire development lifecycle by preventing the two most common causes of project failure: ambiguous requirements and unchecked scope creep.

KEY BENEFITS

  • Prevents costly rework and late-stage pivots
  • Creates measurable checkpoints for predictable progress
  • Eliminates "works on my machine" scenarios
  • Removes subjectivity from quality assurance

CRITICAL SUCCESS FACTORS

  • Formal sign-off at each phase gate
  • Immutable evidence for every requirement
  • Direct traceability from code to requirement
  • Systematic verification against specifications

FROM REACTIVE ART TO PREDICTABLE ENGINEERING

By consistently executing these four phases, teams transform software development from a reactive art into a predictable engineering discipline. The Spec-Driven Development workflow creates a self-documenting, auditable, and evidence-based process that systematically drives up quality, reduces ambiguity, and ensures every feature delivered is a feature validated.

THE AUDIT TRAIL ADVANTAGE

The linkage from Git commit, to task list, to proof artifact forms an unbreakable audit trail from a specific line of code back to the requirement it satisfies. This traceability is non-negotiable and transforms development into a transparent, verifiable process.

SELF-DOCUMENTING PROCESS

Every phase generates artifacts that serve as living documentation, creating a complete project history without additional overhead.

AUDITABLE PROGRESS

Machine-readable commit messages and proof documents enable automated verification and compliance tracking at any point in time.

EVIDENCE-BASED QUALITY

Replaces subjective opinions with verifiable proof, ensuring what was built is exactly what was requested.

This disciplined approach prevents common development pitfalls and ensures that completion is a matter of proof, not opinion. The result is higher quality software, reduced risk, and a development process that scales with organizational growth.
