AI Techniques Inside SDD

How Liatrio's four prompts turn effective AI collaboration patterns into a readable workflow teams can study, discuss, and adapt

Spec-Driven Development is not just a four-step checklist. It is a practical implementation of reusable AI techniques that make work more inspectable, more teachable, and easier to resume without losing the thread.

This matters because SDD exposes those techniques directly in markdown prompts, files, and review points. Instead of asking teams to trust a product's hidden behavior, it gives them a concrete operating model they can read, borrow, and refine.

The sections below show the core techniques, where they appear across SDD-1 through SDD-4, and how they contribute to a more reliable AI-assisted implementation loop.

How the Techniques Map to the Four Steps

Each prompt emphasizes a different part of the workflow, but the techniques overlap. The point is not to memorize jargon. It is to notice the repeatable patterns SDD uses to keep AI work aligned, reviewable, and resumable.

01

SDD-1: Clarify and Scope

Primary techniques: Progressive Disclosure, Task Decomposition, Dynamic Context Injection

Also supports: Structured Outputs, Serialized External State, Human / Resumable Checkpoints, Reasoning Protocols

Example: Start with clarifying questions, stop for answers, review the repo only as needed, then define 2-4 demoable units before locking the spec.

02

SDD-2: Plan in Reviewable Steps

Primary techniques: Task Decomposition, Progressive Disclosure, Structured Outputs

Also supports: Serialized External State, Dynamic Context Injection, Human / Resumable Checkpoints, Reasoning Protocols

Example: Generate parent tasks first, wait for approval, then expand to sub-tasks only after the plan is aligned and the relevant files are known.

03

SDD-3: Execute with Proof

Primary techniques: Serialized External State, Human / Resumable Checkpoints, Evidence-Based Validation

Also supports: Task Decomposition, Structured Outputs, Dynamic Context Injection, Progressive Disclosure

Example: Re-read the task state, implement one unit at a time, capture proof immediately, update status markers, and pause at checkpoints before moving on.

04

SDD-4: Validate with Gates

Primary techniques: Evidence-Based Validation, Structured Outputs, Reasoning Protocols

Also supports: Serialized External State, Dynamic Context Injection, Human / Resumable Checkpoints, Task Decomposition

Example: Discover the current state, verify artifacts independently, apply PASS/FAIL gates, and produce a coverage matrix with explicit conclusions.

What This Looks Like in Practice

These techniques become concrete when you see them in the prompts and artifacts themselves. The goal is not to sound sophisticated. The goal is to make the AI's working method explicit enough that a human can review it, learn from it, and redirect it when needed.

Four Practical Examples from the Workflow

Parent Tasks Before Sub-Tasks

Techniques: Task Decomposition, Progressive Disclosure, Human / Resumable Checkpoints

SDD-2 deliberately reveals the plan in two passes. First it proposes parent tasks for strategic alignment. Only after approval does it expand them into detailed sub-tasks.

Deterministic Files for Resumable Work

Techniques: Serialized External State, Structured Outputs

Specs, tasks, proofs, and validation live in predictable files while the implementation loop is active. That makes it possible to pause, resume, review progress, and keep evidence tied to the work without relying on one chat session's memory.

Just-In-Time Repository Grounding

Techniques: Dynamic Context Injection, Reasoning Protocols

Instead of front-loading every repo detail, the prompts instruct the assistant to inspect the current codebase, patterns, and relevant files at the moment they become useful for the next decision.

Proof and Validation as First-Class Outputs

Techniques: Evidence-Based Validation, Structured Outputs

SDD-3 and SDD-4 do not treat verification as an afterthought. They require proof artifacts, command output, explicit gates, and a final validation report so completion is grounded in evidence rather than confidence.

What You Can Borrow Even If You Do Not Adopt All of SDD

One of the advantages of exposing the workflow in markdown is that teams can reuse the parts that fit their environment. You do not need to adopt the whole playbook to benefit from the underlying patterns.

Add explicit stop points

Before an assistant expands scope or starts implementation, make it pause for review. This alone can reduce drift dramatically.

Persist state outside the chat

Store the working spec, task list, or proof notes in deterministic files so the process can survive interruptions and handoffs.

Use strict output structures

Templates, checklists, and status markers make AI output easier to review and far less likely to dissolve into vague prose.

Require evidence before "done"

Ask for command output, proof artifacts, and clear gates. It is one of the simplest ways to improve trust in AI-assisted work.
